# Подготовка к защите — ТОП-5 вопросов с эталонными ответами (Неделя 7)

### 1. Почему вы выбрали FastAPI, а не Django REST Framework?
FastAPI легче и быстрее для чистого REST API. Главные причины: (1) валидация данных встроена через Pydantic — не нужен отдельный слой сериализаторов; (2) автоматическая интерактивная документация (Swagger/OpenAPI) из коробки; (3) нативная поддержка async и типизации Python. Django REST мощнее для монолитов с админкой и ORM «всё-в-одном», но для нашего узкого API это была бы избыточная сложность. Мы сознательно выбрали инструмент под масштаб задачи.

### 2. Как вы гарантируете, что подписка не будет создана с некорректными датами?
Двухуровневая защита. На уровне схемы Pydantic `model_validator` проверяет `end_date > start_date` ещё до обращения к БД — некорректный запрос отклоняется с кодом 422. При частичном обновлении (PUT) мы пересчитываем итоговые даты после применения изменений и возвращаем 400, если правило нарушено. Дополнительно на уровне БД можно добавить `CHECK`-ограничение — это «последняя линия обороны», если данные попадут в обход API.

### 3. Объясните вашу модель ролевого доступа (RBAC). Как технически реализовано, что удалять подписку может только Admin?
У каждого пользователя есть поле `role` (enum: admin/employee/customer). При логине роль зашивается в JWT. Мы используем фабрику зависимостей `require_roles(...)`: она извлекает текущего пользователя из токена и сверяет его роль со списком разрешённых. Эндпоинт удаления подписки объявлен с `Depends(require_roles(UserRole.admin))`, поэтому employee получает 403 ещё до выполнения бизнес-логики. Обновление объявлено с `require_roles(admin, employee)`. Логика проверки находится в одном месте — это исключает дублирование и ошибки.

### 4. Что произойдёт при удалении компании или тарифа? Расскажите про целостность данных.
Мы задали поведение внешних ключей осознанно. При удалении компании срабатывает `ON DELETE CASCADE` — удаляются её тарифы, клиенты и связанные подписки, чтобы не оставались «осиротевшие» записи арендатора. А вот на `plan_id` в подписке стоит `ON DELETE RESTRICT` — удалить тариф, на котором есть активные подписки, нельзя. Это защищает историческую целостность: нельзя «потерять» тариф, по которому платят клиенты. Email клиента уникален в паре с `company_id`, поэтому один email может обслуживаться разными компаниями.

### 5. Как ваш сложный JOIN-запрос работает и почему вы не делаете N+1 запросов?
Эндпоинт активных подписок клиента выполняет один SQL-запрос с `JOIN` между `subscriptions` и `subscription_plans`, отфильтрованный по `customer_id` и `status = active`. Мы получаем подписку и тариф в одной выборке, а не запрашиваем тариф отдельно для каждой подписки (проблема N+1). Альтернатива в ORM — жадная загрузка через `selectinload`, но явный `JOIN` здесь нагляднее и даёт точный контроль над тем, какие поля попадают в ответ. На больших объёмах индексы по `customer_id`, `plan_id` и `status` обеспечивают производительность.

### Бонус — вероятные дополнительные вопросы
- **Где хранятся секреты?** В переменных окружения (`.env`), файл в `.gitignore`, в репозиторий не попадает. Для деплоя — секреты платформы (Render/Railway).
- **Почему `NUMERIC` для цены, а не `float`?** `float` даёт ошибки округления в деньгах; `NUMERIC(10,2)` хранит точное десятичное значение.
- **Как масштабировать?** Stateless-приложение за счёт JWT (нет серверных сессий) — можно запускать несколько реплик за балансировщиком.
- **Чего не хватает для продакшена?** Alembic-миграции вместо `create_all`, автотесты (pytest), rate-limiting, логирование, автоматическая смена статуса подписки по `end_date` (cron/worker).
